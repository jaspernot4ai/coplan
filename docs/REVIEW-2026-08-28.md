## 🔴 SEC-001：儲存型 XSS（必須修，優先於所有其他任務）

### 問題

使用者可控的資料被直接插進 `innerHTML`，沒有轉義。至少三處：

**1. 行程卡片的提出者**（`public/index.html` 約 422 行）
```js
row2.innerHTML = `[${a.type}]
    <span class="proposer" style="color:${colorOf(a.createdBy)}">${a.createdBy}</span>
    ${a.viaAgent ? "🤖" : "🙋"}`;
```

**2. 活動時間軸**（約 480 行）
```js
div.innerHTML = `
  <b style="color:${colorOf(e.who)}">${... e.who ...}</b>
  <code class="log-action">${e.action}</code>
  <span class="log-summary">${e.summary}</span>`;
```
`e.summary` 由伺服器產生，但內容包含使用者輸入的行程標題。

**3. 成員清單**（約 501 行）與**待確認區的 `location.href`**（約 556 行）

### 攻擊方式

`createdBy` 直接來自網址參數 `?as=`，沒有任何過濾。攻擊者只要把這個連結傳給旅伴：

```
https://coplan.coplan-lab.workers.dev/r/tokyo?as=<img src=x onerror=alert(document.cookie)>
```

自己開一次、隨手新增一筆行程，這個字串就**存進 Durable Object 並廣播給房間裡所有人**，
在每個成員的瀏覽器執行。這是**儲存型 XSS**，不是只影響自己的反射型。

行程標題也是同一條路徑：Agent 或人輸入 `<script>` 開頭的標題 → 進入 log summary → 全員執行。

### 為什麼這對這個作品特別嚴重

這個作品的核心主張是「**我們認真看待 Agent 時代的權限邊界**」——
辛苦做了跨 session 付款閘門，結果任何人都能在別人的瀏覽器裡執行任意程式碼，
那道閘門就沒有意義了（注入的腳本可以直接呼叫 `approveCheckout()`）。
評審若發現，整個安全論述會反過來扣分。

### 修正方式

**加一個轉義函式，所有插進 `innerHTML` 的動態值都經過它。**

```js
// 使用者與 Agent 可以控制的字串（名字、標題、稽核摘要）一律轉義後才進 innerHTML。
// 這個房間是多人共享的，未轉義的字串會存進伺服器並在所有成員的瀏覽器執行（儲存型 XSS）。
function esc(v) {
  return String(v ?? "").replace(/[&<>"']/g, c => ({
    "&": "&amp;", "<": "&lt;", ">": "&gt;", '"': "&quot;", "'": "&#39;"
  })[c]);
}
```

需要套用的位置（全部檢查一次，不要只改上面列出的三處）：
- `renderBoard` 的 `row2.innerHTML`：`${esc(a.type)}`、`${esc(a.createdBy)}`
- `renderLog`：`${esc(e.who)}`、`${esc(e.action)}`、`${esc(e.summary)}`
- `renderMembers`：`${esc(m.name)}`
- `renderApprovals`：`${esc(p.requestedBy)}`、`${esc(location.href)}`
- 其他任何 `innerHTML` 樣板裡的變數

**`colorOf()` 的回傳值不需要轉義**（它只會回傳 PALETTE 裡的固定色碼），但也不要因此養成
「這個應該安全」的習慣——判準是「這個值是不是使用者可以控制的」。

**已經用 `textContent` 的地方不用改**（例如 `titleSpan.textContent = a.title`），
`textContent` 天生安全。

### 驗收

用 `?as=<img src=x onerror=alert(1)>` 開房間並新增一筆行程，
另一個分頁載入該房間 → **不應該跳出任何 alert**，畫面上應該原樣顯示那串文字。

## 🟡 MAINT-002：`?as=` 沒有長度與內容限制

名字沒有上限，超長字串會撐破版面；空白字元也未處理。

## 🟢 通過項目（確認無誤，不需改動）

- **跨 session 確認的邏輯正確**：後端 `msg.sessionId === approval.requestedBySession` 才擋，
  前端在發起的 session 不建立按鈕。雙層防護一致。
- **`sessionId` 刻意不存 localStorage**：正確，存了會讓同機開新分頁失效。
- **`viaAgent` 全部來自呼叫端**：BUG-001 的教訓有落實，沒有其他寫死的地方。
- **`state()` / `save()` 集中化**：新增 `pendingApprovals` 時兩處都有更新，沒有漏。
- **日誌上限 100 筆**：有界，不會無限成長。
- **衝突偵測是純程式邏輯**：無 LLM 呼叫，無外部依賴。
- **沒有任何祕密進入前端**：無 API key、無憑證。origin trial token 是設計上公開的。
- **`otherwise` 路徑安全**：Worker 對未知路徑回 404，沒有意外暴露。

## 🟢 刻意的取捨（不是缺陷，但提交說明應該提及）

- **伺服器不驗證前端傳來的欄位**（型別、範圍、權限）。
  對 demo 是正確取捨，但正式產品必須補。
- **任何人知道房號就能加入與修改**。符合「分享連結」的產品情境，但無存取控制。
