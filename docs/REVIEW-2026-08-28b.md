## 🟡 REV2-001：`renderApprovals` 的 `who` 變數帶 HTML，是唯一還需盯著的插值

```js
const who = p.viaAgent === false
  ? `<b style="color:${colorOf(p.requestedBy)}">${esc(p.requestedBy)}</b>`
  : `🤖 <b ...>${esc(p.requestedBy)}'s Agent</b>`;
text.innerHTML = `${who} requested checkout of ...`;
```

**目前是安全的**：`p.requestedBy` 有 `esc()`、`colorOf()` 只回傳固定色碼。

但這裡出現了一個模式：**一個變數裡裝著已組好的 HTML，再被插進另一個樣板**。
`esc()` 只在建立 `who` 的當下有效，後續任何人若改動這段（例如加上房號、備註、或
把 `who` 換成別的來源），很容易忘記那一層已經是 HTML 而不是純文字，轉義就會漏掉。

**建議（低成本）**：在 `who` 這一行上方加註解：

```js
// who 內含已組好的 HTML：requestedBy 在這裡就要 esc()，
// 之後插進 innerHTML 時不會、也不能再轉義一次。
```

不需要重構。這是「留下警示」而非「改結構」的取捨。

## 🟡 REV2-002：`?reset=1` 不清日誌，且會在時間軸留下大量移除紀錄

`maybeReset` 用逐筆 `remove` 訊息清空行程。後果：

- 每刪一筆就寫一筆 `remove_activity` 日誌，清 10 筆行程 = 時間軸多 10 筆雜訊
- 日誌本身清不掉（現有訊息協定沒有「清空日誌」操作）

**Claude Code 的判斷是對的**：它在註解與回報中說明了「這超出本任務不動 `src/index.js`
的範圍，故意不做」。這是正確的克制。

**但對錄影是實際問題**：`?reset=1` 之後時間軸不是乾淨的，開場畫面會有一整排 remove 紀錄。

**建議修正**（錄影前做，改動很小）：在 `src/index.js` 加一個 `msg.t === "reset_room"` 分支，
一次清空 `items`、`log`、`pendingApprovals`（`members` 保留），前端的 `maybeReset` 改送這一則。
這樣既乾淨、又只有一筆日誌，而且比逐筆刪除少幾十次廣播與寫入。

## 🟢 通過項目

- **白名單是白名單，不是黑名單**：`id` / `createdBy` / `viaAgent` / `paid` / `conflictWith`
  全部由伺服器決定，前端無法指定。付款旗標無法被協定層繞過。
- **限流的計數放在記憶體且隨連線清除**，沒有引入外部服務，符合規格。
- **`seedAttempted` / `resetAttempted` 旗標**避免了 WebSocket 重連時重複執行——
  這是實際會發生的情境（斷線自動重連），不是防禦性程式碼。
- **`?seed=1` 只在房間為空時塞資料**，不覆蓋既有行程，符合驗收條件。
- **英文化沒有動到工具的 `name` 與 `inputSchema`**，行為不變。
- **README 與 LICENSE 已建立**，提交的硬性條件滿足。
- 沒有引入任何新套件、沒有 i18n 框架、沒有 CSS 框架——規格中的「不要做」全部遵守。
